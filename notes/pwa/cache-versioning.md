# Cache versioning

> **In one line:** I put a version in my service worker cache names, delete every cache that does not match the current version in the `activate` event, and use content-hashed filenames like `app.3f9a2c.js` so a changed file always gets a new URL and can be cached forever.

## Key points
- **Two caches to think about:** the browser [HTTP cache](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching) (controlled by headers) and your own [Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache) caches (controlled by your service worker code). Versioning is needed for both.
- **Versioned cache names:** name caches like `shell-v4`. When you ship v5, the new worker writes to `shell-v5`, and `activate` deletes `shell-v4`. Activate is the safe place because the old worker (and the tabs that used it) are gone by then.
- **Cache busting with hashed filenames:** the build tool (Vite, used by SvelteKit) puts a hash of the file content in the name. Same content, same name. Changed content, new name. So the old URL can never serve new code by mistake.
- **Long cache for hashed files, no cache for the entry points:** hashed files get `Cache-Control: max-age=31536000, immutable`. `index.html` and `sw.js` get `no-cache` (meaning "always check with the server first"), because they are what point to the new hashes.
- **Any byte change in `sw.js` is a new version.** Bumping `VERSION` (or a new precache list with new hashes) is what triggers install of a new worker.

## Example
```js
// sw.js
const VERSION = 'v5';                    // bump on each deploy (or inject from the build)
const SHELL = `shell-${VERSION}`;
const RUNTIME = `runtime-${VERSION}`;
const KEEP = [SHELL, RUNTIME];

// Usually generated by the build, with hashed names
const PRECACHE = ['/', '/_app/immutable/entry/app.3f9a2c.js', '/_app/immutable/assets/app.81bd0e.css'];

self.addEventListener('install', (event) => {
  event.waitUntil(caches.open(SHELL).then((c) => c.addAll(PRECACHE)));
});

self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    const names = await caches.keys();           // e.g. ['shell-v4', 'runtime-v4', 'shell-v5']
    await Promise.all(
      names
        .filter((n) => !KEEP.includes(n))         // anything not from this version
        .map((n) => caches.delete(n))             // clean it up
    );
  })());
});
```

In SvelteKit you do not hand-write the list. The [`$service-worker` module](https://svelte.dev/docs/kit/service-workers) gives you `build`, `files` and `version`:

```js
// src/service-worker.js (SvelteKit)
import { build, files, version } from '$service-worker';
const CACHE = `cache-${version}`;   // version changes on every build
const ASSETS = [...build, ...files];
```

Server headers (example, nginx-style idea):

```bash
# hashed assets: cache for a year, never revalidate
/_app/immutable/*   Cache-Control: public, max-age=31536000, immutable
# entry points: always revalidate
/index.html         Cache-Control: no-cache
/service-worker.js  Cache-Control: no-cache
```

## When to use it
- A trading PWA ships fixes many times a day. Hashed filenames mean users never get half-old, half-new JS. Cleaning old caches in `activate` stops the phone's storage from filling with ten old copies of the app.

## Likely questions
### How do you clean old caches?
In the `activate` event I call `caches.keys()`, filter out the names that belong to the current version, and `caches.delete()` the rest, all inside `event.waitUntil` so the worker does not finish activating before cleanup is done. I do it in activate, not install, because during install the old worker may still be serving open tabs from the old cache.

### What is cache busting and why hashed filenames?
Cache busting means making the browser fetch a new file instead of a stale cached one. The best way is to change the URL when the content changes, and a content hash in the filename does exactly that. A query string like `app.js?v=5` also works but some proxies handle it badly, and a version number changes every file even when only one changed. With hashes, unchanged files keep their name, so users only download what actually changed.

### Why can hashed files be cached forever but not `index.html`?
A hashed file's content can never change under the same name, so `immutable` is safe. `index.html` keeps the same URL but points to new hashed files after a deploy, so it must be revalidated every time, or users would load an old HTML that points to the old bundle.

### Should you delete caches you did not create?
No. Filter by your own prefix (for example names starting with `shell-` or `runtime-`), because other code on the same origin, such as a library, may use the Cache API too. Workbox does this with its own prefixed names.

### What happens to an old tab after the deploy?
If the old tab lazy-loads a chunk that was deleted from the server and the cache, you get a chunk load error. Fixes: keep old hashed files on the CDN for a while, do not `skipWaiting` blindly, and show a "new version, refresh" prompt.

## Common mistakes
- Using one fixed cache name (`my-cache`) forever, so old files pile up and never get removed.
- Deleting old caches in `install` instead of `activate`, breaking tabs still on the old version.
- Caching `sw.js` or `index.html` with a long `max-age`, so the update is never seen.
- Forgetting `event.waitUntil`, so cleanup can be cut off when the worker is stopped.
